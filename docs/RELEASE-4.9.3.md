## Mine App 4.9.3 · 双版本更新

### 双版本共同改动

**「限制」的底层机制换成墓碑（Tombstone）**

功能名称和操作方式不变，变的只是底层。

旧机制用的是 `cmd appops set RUN_IN_BACKGROUND ignore`，实测在这台 HyperOS 上**完全不生效**：

| 状态 | 后台进程 | oomAdj |
|---|---|---|
| 未限制 | 5 个 | 500 / 700 / 905 |
| 已限制（旧机制） | **6 个** | 500 / 700 / 905 |

把 `RUN_ANY_IN_BACKGROUND` 也设成 ignore（已设置超过一天）之后，进程照样存活。

**现在换成 `am set-inactive`（Android 官方的 App Inactive 机制）**：

| 状态 | 后台进程 | oomAdj | CPU |
|---|---|---|---|
| 已限制（新机制） | 进程保留 | **900+（cached）** | **零增长** |

实测小红书：设置后三个后台进程的 oomAdj 从 500/700 全部降到 900，进程 CPU 时间在 5 秒内**完全没有增长**（`utime=1849 stime=864` 两次读数相同），说明被 cgroup freezer 真正冻结。

而当你点图标打开它时，AMS 会自动解冻——**同一个进程 PID 原地复活**，状态不丢，秒开。

这就是「墓碑」的效果：不耗电、不联网、不占 CPU，但内存和状态都在。

**升级后自动迁移旧数据**

旧机制下标记过的应用（这台机器上是 95 个）会在升级后**自动转成新机制**，不需要手动重新限制一遍。

迁移状态是**持久化的一次性标记**，和索引状态一样保存：

- 每次启动读一次标记，已经有就直接返回（开销只有一次本地读取）
- 没有才执行迁移，全部成功后才写标记
- 之后无论升到 5.0 还是 6.0，都不会重复迁移

> 只有一种情况会重新检查：手动卸载后重装（应用数据被清空）。这时会再判断一次，成本是几秒，且迁移本身幂等，不会产生副作用。

**两个安全保障**

1. 本 App 不能被自己限制——否则进程被冻，就再也没有入口解除限制了
2. 冻结只作用于后台。桌面、输入法、系统 UI 这些前台工作的应用不受影响；实测限制清单里的 `com.miui.home` 仍是 `oom=100`、输入法 `200`、`com.android.systemui` 是 `fixed 100`

**已知边界**

- 用户主动打开被限制的应用后，系统会自动解冻它（这是 App Inactive 的设计）。想让它重新回到墓碑状态，再点一次「限制」即可
- 收不到后台推送——这是墓碑的代价，和「既要完全冻结又要收消息」本身矛盾
